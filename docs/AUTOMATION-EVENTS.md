# Automation event journal

The local automation API exposes a bounded in-memory event journal through `event.read`. It complements point-in-time methods such as `workspace.list` and `terminal.read`.

## Consumer model

A client should:

1. Call `workspace.list` to obtain the current workspace and pane snapshot.
2. Call `event.read` and save `latestSeq` as its starting cursor.
3. Long-poll with `afterSeq` set to the last processed `nextSeq`.
4. Treat `dropped: true` as a resynchronization requirement and call `workspace.list` again.

The journal is process-local and resets when the desktop app restarts. A cursor from a previous process may therefore move back to the new process's current `latestSeq`.

## Bounds

- Maximum 1,024 retained events
- Maximum 8 KiB serialized payload per event
- Maximum 100 events requested per read
- Maximum 32 KiB serialized event data returned per read
- Maximum 30-second long-poll
- Frontend publishes at most 64 events per IPC batch
- Event kind is limited to lowercase ASCII letters, digits and dots
- Frontend event types are a serde allowlist; arbitrary kind/payload injection is not exposed

The server's normal 64 KiB response cap remains the final transport boundary.

## Request

```json
{
  "version": 1,
  "id": "request-id",
  "token": "token",
  "method": "event.read",
  "params": {
    "afterSeq": 42,
    "maxEvents": 50,
    "waitMs": 30000
  }
}
```

All parameters are optional:

- `afterSeq`: defaults to `0`
- `maxEvents`: defaults to `50`, range `1`–`100`
- `waitMs`: defaults to `0`, range `0`–`30000`

Unknown fields are rejected.

## Response

```json
{
  "version": 1,
  "id": "request-id",
  "ok": true,
  "result": {
    "events": [
      {
        "seq": 43,
        "timestampMs": 1785474000000,
        "kind": "workspace.created",
        "payload": {
          "workspaceId": "workspace-id",
          "title": "Agent",
          "cwd": "C:\\code"
        }
      }
    ],
    "nextSeq": 43,
    "earliestSeq": 1,
    "latestSeq": 43,
    "dropped": false,
    "hasMore": false
  }
}
```

`hasMore` indicates that additional events remain after `nextSeq`, either because `maxEvents` or the serialized byte bound was reached.

## Event kinds

### Workspace

- `workspace.created`
- `workspace.selected`
- `workspace.closed`

### Pane

- `pane.created`
- `pane.updated`
- `pane.closed`

`pane.updated` reports observable title or browser URL changes. Workspace unread state is intentionally excluded.

### Attention

- `attention.requested`
- `attention.cleared`

Attention events are derived from the same React state used to render pane rings and workspace unread indicators. OSC 9/99/777 notifications therefore flow into the event journal without a second parser. The notification panel (`NotificationPanel.tsx`) renders from that same attention state via `buildNotificationItems` — it is a view, not a second source of truth.

### Terminal lifecycle

- `terminal.started`
- `terminal.exited`
- `terminal.closed`
- `terminal.error`

Terminal lifecycle events are published by the Rust PTY backend, not inferred from React. Payloads include session/workspace IDs and the terminal generation. Started events include process ID and shell; exited events include the exit code when available.

## Ordering

The journal provides a single monotonic sequence for events after they reach the Rust store. Events generated by one React state diff are queued and published in order. Terminal lifecycle events originate independently in the PTY backend, so consumers must not assume `pane.created` always precedes `terminal.started`.

Use IDs and the initial `workspace.list` snapshot rather than relying on cross-layer event ordering.

## Frontend publication

React compares the previous and current observable state after each commit and derives events through a pure, tested diff function. The publisher:

- does not emit an initial flood for restored workspaces
- updates its local snapshot before asynchronous IPC
- serializes IPC batches through a promise queue
- continues publishing after an individual failed batch
- normalizes event text to 1,024 Unicode characters and removes NUL characters

## CLI

```powershell
cmux-cli event read
cmux-cli event read --after 42 --max-events 25 --wait-ms 30000
```

The CLI prints the normal machine-readable protocol response. There is no dynamic filter language or raw subscription method in this slice.

## Persistence and privacy

The event journal is memory-only. It is not persisted to disk, localStorage or the automation discovery file. Terminal output itself is not copied into the event journal; use `terminal.read` for bounded transcript access.
